O Diagnóstico da Crise: Quando o Link Físico Rompeu

Análise forense do incidente em que um corte de infraestrutura expôs o perigo de adotar uma solução de banco única e ingênua para requisitos com naturezas opostas de negócio.

09:42 BRT • Falha Crítica de Conectividade

Rompimento de Fibra Óptica: Partição de Rede Real ('P')

Durante obras civis em rodovia interestadual, o duto primário e o enlace de redundância de fibra óptica conectando o Data Center Sul (SP-01 - Primário) e o Data Center Norte (RJ-01 - Secundário) foram rompidos simultaneamente. Em segundos, os dois polos de processamento da PaySeguro ficaram completamente isolados um do outro, impedindo qualquer sincronismo síncrono ou replicação tradicional.

Causa Raiz Partição de Rede (P no Teorema CAP). Os nós estavam vivos, mas incomunicáveis.
Efeito no Legado Arquitetura ingênua com consistência eventual causou "Saldos Fantasma" e saques concorrentes.
Prejuízo Potencial Risco regulatório no Banco Central (BACEN) por quebra de liquidez e conciliação bancária.

Fundamento Teórico

O Teorema CAP Explicado à Diretoria Executiva

Em sistemas de computação distribuída com múltiplos data centers, falhas de comunicação não são hipóteses: são certezas estatísticas. Por que a física nos força a escolher entre Consistência ou Disponibilidade?

C

Consistência (Linearizabilidade)

Toda leitura subsequente a uma escrita bem-sucedida deve retornar obrigatoriamente o valor mais recente ou falhar com erro.

Regra Financeira: Um cliente nunca pode ler um saldo de R$ 1.000 se acabou de transferir R$ 900.
A

Disponibilidade (Availability)

Todo nó não-falho responde a qualquer requisição recebida com sucesso (sem erro de indisponibilidade ou timeout), sem garantia de ser a versão mais recente.

Regra de UX: O usuário abre o app e a interface nunca exibe uma tela travada com erro 503.
P

Tolerância a Partição (Partition Tolerance)

O sistema continua operando mesmo quando mensagens entre servidores são perdidas, atrasadas ou quando a rede é partida em duas.

Fato Inevitável: Em redes reais com mais de um data center, P não é negociável. Cabos rompem.

Simulador de Decisão CAP para a Diretoria

Como P é mandatório no mundo físico, selecione o comportamento desejado durante uma partição:

Decisão Arquitetural 01 • Transacional / Saldos

Saldos Bancários: Foco em CP com MongoDB

Prioridade absoluta: Integridade Numérica Estrita. Dinheiro não aceita aproximações.

MongoDB Enterprise Replica Set

Justificativa Técnica de Negócio

Em transações financeiras (Pix, saques, pagamentos de boletos), a consistência eventual é catastrófica. Se dois nós aceitarem débito simultâneo sem comunicação, o saldo é duplicado (Double Spending).

Ao escolher o modelo CP (Consistency + Partition Tolerance) com MongoDB, assumimos que, se houver partição de rede, qualquer nó que não pertença à maioria de quórum rejeitará imediatamente a operação de escrita em vez de registrar um saldo errôneo.

✓
Quórum e Eleição de Primary: MongoDB utiliza consenso distribuído (estilo Raft). Se o Primary ficar na minoria isolada, ele se auto-rebaixa para Secondary e recusa escritas.
✓
Write Concern w: "majority": O débito de saldo só é confirmado ao cliente após gravação persistente na maioria estrita dos nós ativos.
✓
Read Concern "linearizable": Garante que nenhuma leitura retorne dados obsoletos ou provenientes de um Primary órfão particionado.
mongodb-wallet-service.js (Configuração CP Estrita) 
// PaySeguro: Transação de Saldo Atômico com Quórum Estrito
const { MongoClient } = require('mongodb');

const client = new MongoClient(process.env.MONGO_URI, {
  // 1. Write Concern Obrigatório: escrita confirmada na MAIORIA
  writeConcern: { w: 'majority', wtimeoutMS: 5000 },
  // 2. Read Concern Obrigatório: impede leitura de Primary isolado
  readConcern: { level: 'linearizable' },
  // 3. Apenas nós que participam do quórum respondem
  readPreference: 'primary'
});

async function efetuarDebitoSeguro(userId, valorPix) {
  const session = client.startSession();
  try {
    return await session.withTransaction(async () => {
      const wallets = client.db('payseguro').collection('wallets');
      
      // Atualização condicionada: garante saldo suficiente
      const res = await wallets.updateOne(
        { _id: userId, saldo: { $gte: valorPix } },
        { $inc: { saldo: -valorPix }, $set: { lastUpdate: new Date() } },
        { session }
      );

      if (res.matchedCount === 0) {
        throw new Error('Saldo insuficiente ou bloqueio concorrente');
      }
      return { status: 'DEBITADO_COM_QUORUM' };
    });
  } catch (err) {
    // Em caso de partição, o nó sem quórum falha rápido (fail-fast)
    return { status: 'REJEITADO_PARTICAO_SEGURA', motivo: err.message };
  } finally {
    await session.endSession();
  }
}
Decisão Arquitetural 02 • Alta Concorrência / Notificações

Feed de Notificações: Foco em AP com Apache Cassandra

Prioridade absoluta: Disponibilidade Máxima Ininterrupta. O app nunca pode ficar fora.

Apache Cassandra Ring Multi-DC

Justificativa Técnica de Negócio

O feed de notificações (alerta de transação recebida, promoções, avisos de cashback) precisa responder instantaneamente a milhões de usuários. Se uma notificação for entregue com 3 segundos de atraso ou fora de ordem estrita, o negócio não sofre prejuízo financeiro.

Ao escolher o modelo AP (Availability + Partition Tolerance) com Cassandra, garantimos que qualquer nó do cluster aceita escritas e leituras, mesmo que o cabo entre data centers esteja partido. A consistência é eventual.

✓
Arquitetura Masterless (Peer-to-Peer): Não existe nó primário nem eleição. Todos os nós coordenam e gravam independentemente, eliminando Single Point of Failure (SPOF).
✓
Tunable Consistency (Consistência Ajustável): Utilizamos nível LOCAL_QUORUM ou ONE. Uma escrita no Data Center RJ-01 é concluída localmente sem esperar a fibra de SP voltar.
✓
Hinted Handoff & Read Repair: Assim que a fibra é restaurada, os nós trocam mutações pendentes via gossip protocol automaticamente em background.
feed_notifications.cql (Cassandra Multi-DC Schema) 
-- PaySeguro: Keyspace com Replicação Geográfica Multi-Datacenter
CREATE KEYSPACE payseguro_feed
WITH replication = {
  'class': 'NetworkTopologyStrategy',
  'DC_SP01': 3,  -- 3 réplicas em São Paulo
  'DC_RJ01': 3   -- 3 réplicas no Rio de Janeiro
};

-- Tabela particionada por usuário e ordenada temporalmente
CREATE TABLE payseguro_feed.notifications (
  user_id uuid,
  notification_id timeuuid,
  category text,
  title text,
  body text,
  is_read boolean,
  PRIMARY KEY ((user_id), notification_id)
) WITH CLUSTERING ORDER BY (notification_id DESC);

-- Consulta com consistência LOCAL_QUORUM:
-- Opera com disponibilidade 100% mesmo se a fibra inter-DC romper!
CONSISTENCY LOCAL_QUORUM;

Recomendação Final da Engenharia

O Teorema CAP não é uma limitação, é uma bússola de projeto

Tentar forçar um único banco de dados genérico para resolver saldos financeiros e feeds de notificações é um erro fatal que culmina ou na falência por saldos fantasmas ou no congelamento completo da experiência do cliente. A solução elegante implementada pelo Grupo 3 utiliza a especialização poliglota: MongoDB no perfil CP assegura fidelidade matemática irrevogável, enquanto Apache Cassandra no perfil AP garante que a PaySeguro permaneça viva e ágil em qualquer tela.
